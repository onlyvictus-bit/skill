# Cortex: actual requirement-driven routing

Read the preserved [Cortex source](specialists/cortex/SKILL.md) after this adapter.

## Input

Use the exact request, opened repository instructions, existing requirements and approval scope, the current available-skills catalog, and observed tool/runtime availability. Do not treat every installed skill as callable code.

## Procedure

1. Extract every explicit deliverable, constraint, negative requirement, format/count, and acceptance condition. Give independently droppable details separate IDs. Preserve ambiguous items as unresolved.
2. Sweep implied prerequisites: source/provenance, domain knowledge, output format, verification type, scale, error paths, money/privacy/external effects. Classify each Blocking, Required, Recommended, Future, or Rejected. Add only accepted requirements to Fable.
3. Scan catalog metadata for coverage. Open candidate definitions whose behavior is needed; resolve paths and runtime dependencies. Prefer a relevant specialist over a generic reader, but current primary evidence overrides a stale skill.
4. Write one row per need: `need ID | explicit/implied | capability | skill/path | stage | availability | output | verification | gap disposition`.
5. Select the smallest sufficient roster. A multi-part implementation generally needs Fable plus only its relevant specialists. At more than eight active helpers, split the work into phases and load references progressively. Do not load unrelated skills for ceremony.
6. Run process/evidence inside Fable; use Deep Plan for consequential alternatives, Blueprint for design, and Triangulate for multi-origin judgments. These are capabilities, not a second fixed approval system. If only one independent origin exists, report that gap rather than inventing a Triangulate result.
7. Announce the concise selected roster and gaps. Execute selected adapters in dependency order. On new requirements or missing runtime, revise the affected roster and plan; preserve prior decisions and explain the change.
8. Import accepted outputs to the canonical requirement/plan/test records. At delivery, report what each used helper actually contributed; omit claims for uninvoked helpers.

## Output and checks

Store the roster and gap dispositions in a planned report path and record Cortex in `specialists.json`. Independently compare the roster back to the user's complete request: every explicit need must have a capable route and verification or a visible blocker. An unavailable dependency cannot count as covered. Remove one needed capability in a scratch example and confirm the missing need becomes a gap. This is a model-followed reasoning procedure; the gate checks mappings and freshness, not whether every English requirement was understood correctly.

## Failure handling

Do not recursively invoke Cortex -> Autonomous Operator -> Fable -> Cortex. Run one intake/rerouting pass per changed requirement basis. Do not spawn agents merely because the source calls the roster a team. Follow the host's agent policy; use views sequentially in the current task where appropriate. Missing specialists can have explicit manual fallbacks, but label those as fallbacks and verify the required outcome.
