## Recommended build

**Add Semantica as a governed knowledge layer inside your Memory Integrity workflow—not as a replacement for Fable, not as a second project manager, and not as another independent memory system.**

The combined system should answer four different questions:

| Component | Question it owns |
|---|---|
| **Fable** | What are we trying to accomplish, what is authorized, and what evidence is required before declaring completion? |
| **Memory Integrity + claude-mon** | Which exact sources and requests were processed, what remains incomplete or stale, and what can safely resume? |
| **Semantica** | Which facts, entities, relationships, and relevant source passages help solve this task? |
| **Knowledge-gap audit + semantic verification** | Where did information disappear or become misrepresented, and does the result actually agree with its evidence? |

**My recommended architecture is one user-facing workflow, one approval authority, one protected execution history, and an optional Semantica knowledge engine.** The sections below specify that build, including downward execution, upward evidence, cross-component connections, and acceptance tests.

This is the integration-design stage. No source files, commits, or remote branches were changed.

## 2. Choose the integration mechanism

I compared three approaches:

| Approach | Benefit | Main limitation | Decision |
|---|---|---|---|
| **Manual export/import bridge** | Small change: export source references into Semantica and inspect results manually. | Useful baseline, but does not provide automatic request binding, invalidation, or end-to-end audit. | Keep as a diagnostic fallback. |
| **Thin governed adapter with an isolated local Semantica worker** | Reuses your existing controls while adding graph, search, provenance, and evaluation capabilities. | Requires explicit contracts and worker qualification. | **Recommended first complete build.** |
| **Distributed knowledge platform** | Shared graph services, multiple workers, remote access, broader analytics. | Adds deployment, permissions, synchronization, migration, and operational failure modes. | Defer until measurements justify it. |

The selected design is a **thin adapter**, but not merely a few import statements. Its essential job is to translate between Semantica’s knowledge objects and your existing source identities, processing evidence, permissions, and completion requirements.

The weakest assumption is that the extracted relationships will improve task-relevant retrieval enough to justify their maintenance and processing cost. The cheapest useful test is a small, real-library prototype that must retrieve a cross-file dependency and then correctly invalidate it after its source changes.

## 3. The complete architecture

The following is the **proposed** structure:

```text
USER GOAL + CONSTRAINTS
          |
          v
FABLE: REQUIREMENTS, APPROVALS, COMPLETION RULES
          |
          | task identity, permitted operations, required evidence
          v
MEMORY INTEGRITY: SOURCE SCOPE AND CURRENT SOURCE BASIS
          |
          +--------------------------+
          |                          |
          v                          v
DIRECT SOURCE PATH             KNOWLEDGE BRIDGE
Open code/documents            Contract and capability checks
Read required units            Source/permission validation
          |                          |
          |                          v
          |                    SEMANTICA WORKER
          |                    Entities and relationships
          |                    Semantic search + graph traversal
          |                    Provenance + ontology validation
          |                          |
          |                          v
          |                    CANDIDATE EVIDENCE
          |                    Source IDs, paths, scores,
          |                    derivations, uncertainty
          |                          |
          +------------+-------------+
                       |
                       v
EVIDENCE PACK: REOPENED SOURCES + REQUIRED CONSTRAINTS
                       |
                       v
CLAUDE-MON: EXACT REQUEST, BUDGET, APPROVAL, EXECUTION RECEIPT
                       |
                       v
AUTHORIZED MODEL / CODING HOST
                       |
                       v
ANSWER OR PROPOSED CODE CHANGE
                       |
             +---------+----------+
             |                    |
             v                    v
CODE / RUNTIME TESTS       KNOWLEDGE-GAP + SEMANTIC AUDIT
             |                    |
             +---------+----------+
                       |
                       v
FABLE: ACCEPT, REOPEN, BLOCK, OR REQUEST A DECISION
                       |
                       v
VERIFIED HANDOFF / RESUME STATE
```

### What flows downward

Goals, constraints, allowed operations, source scope, selected evidence, and exact requests.

### What flows upward

Observed results, failures, source-linked findings, request receipts, test evidence, and readiness decisions.

### What must never flow automatically

A graph suggestion must not become an approved requirement. A model-generated statement must not become an authoritative source. A successful retrieval must not become a complete-read receipt. A passing evaluation must not authorize a commit, push, deployment, or external call.

Your existing source-basis design already separates Fable’s authority from derived Graphify and memory indexes. Semantica should join the derived-information side of that boundary.

## 4. Downward execution: how a task moves through the system

### Fable establishes the task contract

Fable supplies the approved task, requirements, acceptance criteria, applicable project policies, and permitted actions.

For a coding task, this might mean:

> Change retry behavior in the client and worker, preserve the public interface, add regression tests, and do not push.

Semantica may help discover relevant implementation paths. It must not reinterpret “do not push” or expand the authorized change.

### Memory Integrity establishes the actual source basis

Record the repository commit, relevant dirty-file hashes, required documents, source versions, exclusions, and extraction status.

A branch name alone is insufficient because its contents can move. A remote commit alone is also insufficient when the working tree contains relevant changes.

This is where we decide whether the task needs **selective relevance reading** or **complete coverage of a declared scope**. Your existing repository guidance and source-basis contract make this distinction explicit. 

### Semantica discovers related evidence

The bridge sends Semantica a scoped request containing the task question, permitted source set, graph generation, and search limits.

Semantica returns candidates with source references and relationship paths—not an authoritative final answer.

For coding, use structural extraction for declarations, imports, and references wherever practical. Use semantic extraction for prose relationships such as “this architecture decision supersedes that requirement.” Do not treat an embedding match as proof that one function calls another.

### Memory Integrity turns candidates into an evidence pack

Reopen the actual source units. Check their hashes, accessibility, relevance, and applicable review requirements.

The pack must preserve mandatory requirements and exceptions. Ranking may decide which optional context fits; it must not silently remove required constraints.

Every excluded candidate needs an intelligible reason, such as irrelevant, stale, duplicate, unauthorized, or outside the request budget.

### claude-mon controls the final request

The final serialized request—not an earlier approximation—must be measured and bound to the task, evidence pack, model/provider configuration, and authorization.

This boundary also applies to model-backed entity extraction, embedding services, reranking, and evaluation. Those are model or service calls too.

The current companion explicitly declares `live_dispatch=false` and `live_counting=false`. Therefore, the first integration must remain offline or use separately qualified host-observation paths; calling Semantica’s model APIs must not become a bypass. 

### Results return for verification

An answer goes through claim and source checks. A code change goes through those checks **and** executable tests, relevant regressions, and runtime observations.

A well-supported explanation of a patch does not prove the patch works.

## 5. Upward evidence: how the system explains and revises its conclusions

The reverse chain should be navigable:

```text
Completion claim
    -> applicable requirement and acceptance criterion
    -> observed test/result
    -> executed code snapshot or generated answer
    -> exact request and evidence pack
    -> retrieval receipt and graph generation
    -> assertion, relationship, or inference rule
    -> source unit and source version
    -> original approved source basis
```

This chain serves three purposes.

**Explanation:** “Why was this file changed?” should lead to the requirement, relevant source passages, and tests—not just a model’s retrospective explanation.

**Disagreement resolution:** “This conclusion is wrong” should reopen the particular source units, interpretation, or test oracle that supports it.

**Selective invalidation:** “This architecture document changed” should identify dependent facts, summaries, decisions, and evidence that require rechecking.

For inferred facts, store the rule and premises. A traversal path only explains how a result was found; it does not automatically prove that the result logically follows.

Semantica provides entity, relationship, and chunk provenance facilities, including `ProvenanceManager` and `get_lineage`. The integration should map those records back to your original unit identities rather than replacing the existing proof history. 

**Fable retains completion authority; claude-mon retains protected execution history; Semantica provides a queryable projection of knowledge and lineage.**

## 6. Add the nine Semantica capabilities you selected

Semantica’s documented modules provide the graph, extraction, reasoning, search, and provenance building blocks. Their existence is evidence of available mechanisms—not evidence that this combined system already works. [GitHub](https://github.com/semantica-agi/semantica?utm_source=chatgpt.com)

| Capability | Proposed addition to your skill | Required safeguard |
|---|---|---|
| **Semantic search** | Search code explanations, requirements, documents, and decisions by meaning as well as identifiers. | Return source units; similarity is not truth or completeness. |
| **GraphRAG** | Combine search candidates with graph relationships before building the evidence pack. | Bound traversal and validate every retained dependency. |
| **Multi-hop discovery** | Follow requirement → component → interface → test or decision → policy → affected service. | Distinguish traversal from logical inference; retain the path and source basis. |
| **Entity relationships** | Connect project entities across files and documents. | Preserve fully qualified identifiers; do not merge similar names automatically. |
| **Provenance graph** | Answer “where did this assertion come from?” across extraction and interpretation steps. | Link to existing source/receipt identities; do not invent a second authoritative ledger. |
| **Ontology / SHACL** | Validate the structure of project facts and relationships. | Treat skipped or failed validation as unverified, not conforming. |
| **Knowledge graph** | Maintain a persistent, versioned project knowledge projection. | Keep it rebuildable and separate from canonical requirements and source files. |
| **Answer/evaluation tooling** | Evaluate retrieval, source fidelity, task outcomes, and repeated-run stability separately. | Retain errors, unknowns, denominators, and evaluator limitations. |
| **Pipeline-gap diagnosis** | Observe source → extraction → retrieval → prompt → answer transitions. | Collect real stage evidence; do not infer observations from caller assertions. |

### An important GraphRAG implementation choice

Start with **local retrieval that combines vector and graph results**.

In the inspected source, `ContextRetriever.retrieve()` supports `truth_filter` only in `mode="local"`. It explicitly rejects that filter for other modes. Its `mode="hybrid"` includes global retrieval, so “hybrid vector-plus-graph search” and the literal `mode="hybrid"` must not be confused.  

Global search, community summaries, and DRIFT search should be later capabilities with separate provenance, permission, budget, and freshness qualification.

### An important ontology choice

Start with a small, reviewed project schema, not an automatically generated ontology that immediately governs itself.

Useful initial concepts are:

```text
Requirement, SourceVersion, SourceUnit, Component, Symbol,
Interface, TestCase, TestRun, Decision, Assertion, AuditFinding
```

Useful relationships include:

```text
DEFINED_IN, REFERENCES, DEPENDS_ON, IMPLEMENTS, TESTS,
SUPPORTED_BY, CONTRADICTS, SUPERSEDES, DERIVED_FROM
```

A `TESTS` relationship is not equivalent to a successful `TestRun`.

Semantica offers ontology quality checks and SHACL validation. SHACL validates graph constraints; it does not establish that an assertion accurately represents reality or that generated code is correct.  [W3C](https://www.w3.org/TR/shacl/?utm_source=chatgpt.com)

## 7. Avoid a circular dependency: discovery versus qualified evidence

My earlier suggestion—“ingest only fully verified sources”—needs refinement.

Requiring complete processing of an entire corpus before allowing semantic discovery can defeat the purpose of discovery.

Use **two logical views**, preferably over the same stored objects:

### Discovery view

Authorized sources with frozen identities may be indexed to find relevant material. Extraction and interpretation status remain visible.

Results from this view are navigation candidates. They cannot satisfy complete-read requirements or support a high-assurance completion claim by themselves.

### Evidence-qualified view

An assertion becomes eligible to support a particular task only when its applicable source, extraction, processing, provenance, and review requirements pass.

Qualification is **task-relative**. A source may be suitable for locating an API name without being suitable for proving that every exception in a policy was analyzed.

The resulting sequence is:

```text
Identify and freeze
    -> discover candidates
    -> reopen required source units
    -> perform required processing and checks
    -> admit qualified evidence
    -> act
```

For a complete audit, enumerate the required source scope independently of the knowledge graph. Otherwise, anything the extraction process omitted could disappear from both the graph and the audit denominator.

## 8. Define the contracts between components

The names below are **proposed logical contracts**, not claims that these classes already exist.

| Contract | Essential contents | Producer → consumer |
|---|---|---|
| **Source reference** | Workspace, repository, source hash, unit ID, locator, authority, access scope. | Existing Memory Integrity records → bridge. |
| **Graph-build manifest** | Source manifest reference, source-basis digest, extractor identity, ontology version, embedding configuration, graph generation. | Bridge → verifier and retrieval. |
| **Assertion record** | Subject/predicate/object, polarity, conditions, source units, derivation, review status, temporal scope. | Extractor or approved importer → graph. |
| **Retrieval receipt** | Query identity, graph generation, scope, candidates, retained IDs, exclusions, paths, limits reached. | Semantica adapter → evidence assembler. |
| **Evidence pack** | Exact selected units, mandatory constraints, source references, omissions, coverage obligations. | Memory Integrity → claude-mon. |
| **Request/response receipt** | Existing execution identities plus evidence-pack and graph-generation bindings. | claude-mon → auditor. |
| **Audit result** | Observed stage states, claim mappings, findings, metric denominators, uncertainty, source references. | Auditor → Fable. |

An assertion should preserve conditions, not merely a flattened sentence. For example:

```text
Assertion: retries are permitted
Condition: operation is classified as read-only
Exception: caller explicitly disables retries
Source: policy unit U017, exact version H
```

Dropping the condition changes the meaning even though the same entity names remain.

### Version contracts deliberately

Your source-basis reference explicitly warns against adding unknown fields to schemas that reject them. A versioned bridge contract and controlled migration are necessary. 

Also, the existing `fable_bridge_v2.py` composes supplied layer verdicts. The new knowledge route must generate those verdicts from fresh artifact verification; accepting a caller-written `"READY"` would not prove graph or source integrity. 

Preserve existing receipts as historical evidence. Do not retrofit them with invented graph, prompt, or semantic observations.

## 9. Upgrade the knowledge-gap auditor before using it as a gate

The existing patch is a useful deterministic core. It needs an observation and semantic-verification layer around it.

### Separate transport from meaning

Use distinct measures:

**Prompt inclusion:** Did an evidence unit actually appear in the final request?

**Answer coverage:** Which required propositions were correctly addressed?

**Source support:** Which answer propositions are supported by current, admissible sources?

**Contradiction and staleness:** Which propositions conflict with those sources or use an inapplicable version?

The existing overlap metric should be renamed or explicitly labeled as prompt-ID overlap in a versioned API. It must not become a “truth score.”

### Preserve unknown observations

A stage can be observed and empty, partially observed, failed, or unobserved. These states are different.

Missing instrumentation must not produce a source gap or zero coverage. It should produce an audit limitation or block a gate that requires that observation.

### Do not create the expected answer from the same retrieval result

Expected claims should come from approved requirements, a separately curated evaluation set, or a reviewed task specification.

Otherwise:

```text
Retriever returns three claims
    -> evaluator defines those three as the complete requirement
    -> coverage is always perfect
```

That would measure consistency with the retriever’s own omissions.

### Handle derived and reappearing information

A claim may be inferred from several premises, appear through a tool result, or reappear in the answer despite being absent from the prompt.

Consequently, “first missing stage” is a useful **observed-loss diagnostic**, not universal proof of causation. Record derivation paths and alternate evidence paths rather than automatically blaming the model.

### Keep semantic review independently qualified

Your current semantic module performs useful checks for numbers, negation, and declared dependencies, and explicitly says these are not proof of understanding. Reuse those checks; extend them with source-linked proposition and condition matching. 

Model-based judgments need their own evidence class, calibration cases, and uncertainty. The same model repeating its own conclusion is not an independent witness.

## 10. Long-project behavior: change, resume, failure, and security

### Source changes must invalidate dependent knowledge

The proposed invalidation chain is:

```text
Changed source version
    -> affected units
    -> extracted assertions and relationships
    -> embeddings and summaries
    -> dependent retrieval/evidence packs
    -> affected decisions and completion evidence
```

Historical artifacts remain available for historical questions. They must not silently support a current task.

Use the graph to identify affected areas, but also cross-check explicit source references, imports, changed files, and declared requirements. An incomplete graph cannot prove that no other dependency exists.

### Separate three different times

Store when a fact is valid, when its source was observed, and when the index was built. A newly built index can contain an obsolete fact; a recently downloaded document can describe an old event.

For code, branch and working-tree scope are also essential. Similar symbols on two branches are not interchangeable evidence.

### Publish graph generations atomically

Build a new generation separately, validate its manifest and required constraints, then switch readers to it.

Start with one index writer and bounded readers. A crash must not expose a mixture of old and new graph/vector data.

There is no reason to promise one transaction across every store. Instead, retain an operation identity, immutable build artifacts, and recoverable publication state.

### Preserve uncertain execution

A timeout after sending a provider request is not proof that nothing happened. Retain an unknown-delivery state and reconcile before retrying.

Do not promise exactly-once external execution unless the actual provider and adapter support and demonstrate it.

### Enforce permissions before disclosure

Permission filtering must apply to initial search, every graph hop, source reopening, summaries, evidence packs, and exports.

Filtering only the final paragraph is insufficient: hidden node names or relationships can already disclose information.

Source contents remain data, not instructions. A retrieved document cannot authorize a command, change a policy, or trigger a new connector call.

### Define degradation explicitly

When Semantica is unavailable, ordinary coding work may continue through direct source inspection **when the task does not require graph-backed evidence**. The report must show degraded knowledge capability.

When graph traversal, lineage, or complete audit is a required acceptance condition, its failure blocks that outcome. It must not be relabeled as a successful fallback.

## 11. Package it without destabilizing the existing skill

Keep **Memory Integrity as the user-facing entry point** and retain the explicit, version-matched claude-mon companion.

Do not combine the companion packaging redesign with this integration. That would introduce a second migration risk.

A proposed layout is:

```text
memory-integrity/
  SKILL.md                         # Compact routing changes
  references/
    semantica-integration.md        # Ownership and workflows
    knowledge-contract.md          # Versioned bridge schema
    knowledge-operations.md        # Recovery and operating modes
  scripts/
    memory_integrity_workflow.py    # Existing public front door
    knowledge_bridge/
      contracts.py
      worker_client.py
      indexing.py
      retrieval.py
      trace_adapter.py
      verification.py
  tests_knowledge/
    ...

claude-mon/
  scripts/complete_read_v2/
    ...                            # Targeted contract changes only

semantica-runtime/
  pinned environment               # Separate installed runtime
```

These are planned additions, not existing files.

### Why an isolated worker

Semantica’s dependency set and Python upper bound make an isolated runtime safer than making every Memory Integrity invocation import it. A Python 3.14 host, for example, cannot simply assume the inspected Semantica release is supported in the same interpreter. 

Start with a local subprocess protocol, explicit paths, bounded messages, timeouts, and no network listener. Preserve the dependency-light core.

Pin the Semantica revision, bridge schema, ontology, and model configuration. Install only required extras—not the entire feature bundle.

### Keep one generation path

Use Semantica for retrieval and knowledge operations. Do not use its answer-generation convenience methods as a parallel path around the protected request workflow.

Similarly, reuse the accepted document-extraction and canonicalization path. Semantica should consume those canonical units rather than independently parse the same document and produce a competing source identity.

## 12. How the combined skill would be used

### Ordinary coding

A developer asks to change retry handling.

Fable establishes scope. Memory Integrity freezes relevant sources. Semantica finds the policy, client implementation, worker implementation, and related tests. The evidence assembler reopens them and preserves the policy exception. The coding host makes a change, and tests verify behavior.

The graph helps **find what matters**. It does not replace reading or testing.

### Long-running architecture work

A new session asks why a subsystem uses a particular interface.

The system retrieves the decision and supporting sources, checks whether either has been superseded, and returns the applicable rationale with its version. It does not merely retrieve yesterday’s summary and assume it is current.

### Research or document-heavy work

The graph connects claims, methods, supporting passages, contradictions, and later revisions. Memory Integrity separately reports which sources were processed and which extraction or interpretation gaps remain.

Finding a relationship does not mean all related literature was searched.

### High-assurance review

The user declares a complete audit scope. The source manifest defines the denominator; graph discovery identifies additional candidate relationships; every required unit receives the required processing evidence.

The final result distinguishes source identity, extraction, coverage, semantic audit, memory, and persistence rather than collapsing them into “complete.”

## 13. Build in verifiable stages

| Stage | Build outcome | Exit evidence |
|---|---|---|
| **M0 — Freeze and qualify the baseline** | Pin both repositories, the local audit patch, contracts, and required feature scope. | Existing relevant checks reproduced where runnable; unavailable layers recorded. |
| **M1 — Establish the bridge** | Capability handshake, isolated worker, source-reference contract, no model calls. | Real Semantica graph operation succeeds; wrong versions and mismatched source hashes are refused. |
| **M2 — Build the knowledge projection** | Source-linked assertions, typed relationships, reviewed ontology, generation manifests. | Positive graph case plus rejection of missing sources, invalid endpoints, and malformed assertions. |
| **M3 — Add governed retrieval** | Semantic/vector search, bounded local graph expansion, source reopening, evidence packs. | Known multi-hop result retrieved; stale, unauthorized, and over-budget candidates handled correctly. |
| **M4 — Bind requests and traces** | Evidence-pack identity reaches the final request and response receipts. | A retrieved-but-omitted constraint produces a context-gap finding. |
| **M5 — Strengthen semantic auditing** | Separate inclusion, support, contradiction, and uncertainty measures. | Adversarial cases reject reversed conditions, unsupported claims, and misleading ID overlap. |
| **M6 — Qualify lifecycle behavior** | Source drift, restart, cancellation, incomplete builds, and unknown-delivery recovery. | Fault injection demonstrates safe resume without fabricated completion or blind resend. |
| **M7 — Benchmark and release** | Held-out comparisons, matching package manifests, documentation, rollback, installed-copy verification. | Demonstrated benefit with no new safety regressions; publication only under explicit authorization. |

The **first end-to-end prototype** should be deliberately small: a handful of source files, one specification, one decision, one contradiction, and one two-hop dependency.

Then deliberately change a source byte, revoke access to one node, remove one prompt unit, and interrupt one index build. The system must identify the resulting problems before a larger deployment is justified.

No live provider, embedding service, native write, or installed-copy replacement is implied by an offline prototype.

## 14. Measure whether the combination is actually better

Use the same tasks, source versions, model settings, tools, and resource budgets across four configurations:

| Configuration | Purpose |
|---|---|
| **Fable + Memory Integrity + direct inspection** | Baseline for your present workflow. |
| **Baseline + vector/semantic search** | Measures the benefit of semantic retrieval without graph traversal. |
| **Baseline + governed Semantica GraphRAG** | Measures the additional benefit of relationships. |
| **GraphRAG + full trace and semantic audit** | Measures the additional detection benefit and overhead. |

Measure task success, missed requirements, unnecessary edits, regressions, retrieval evidence quality, stale-source use, recovery correctness, latency, model usage, and storage growth.

Measure initial indexing separately from repeated-session work. A system that is expensive on its first run may still be worthwhile over months; a system that rebuilds everything after every small edit may not be.

Use held-out cases and repeated runs for nondeterministic paths. Include negative cases where the correct outcome is “evidence missing,” “conflict unresolved,” or “action not authorized.”

**Promotion condition:** enable graph-backed behavior by default only for workloads where it demonstrates a useful improvement over the simpler baseline without weakening source integrity, permissions, or correctness.

**Pivot condition:** when graph extraction creates more misleading relationships or maintenance cost than retrieval benefit, keep semantic search and source-linked provenance, but reduce or disable automatic graph expansion.

---

## Final recommendation

Build the combination in this form:

> **Fable controls the work. Memory Integrity establishes the source basis. claude-mon preserves the execution evidence. Semantica discovers and organizes knowledge. Tests and semantic auditing challenge the result.**

The highest-value additions are **source-linked knowledge graphs, governed semantic retrieval, bounded multi-hop discovery, provenance, and real stage instrumentation**. Ontology enforcement and stronger semantic evaluation should follow the first working path; distributed infrastructure and autonomous global search should wait for evidence.

The central acceptance condition is not “all four components are connected.” It is:

**For every consequential result, the system can identify the applicable requirement, reopen the supporting source versions, show the observed processing path, expose missing or conflicting evidence, and refuse completion when a required check is unverified.**

That is the combined capability worth building.
